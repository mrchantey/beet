# beet_infra

Infrastructure as code for beet, built on [OpenTofu](https://opentofu.org).

Cloud resources are declared as Bevy entities and exported to Terraform/OpenTofu JSON, so a beet app can plan, deploy and destroy its own infrastructure. The deploy examples (`lambda`, `fargate`, `lightsail`) stand up the router example on AWS.

- `terra` - build and export OpenTofu JSON configurations
- `bindings` - pre-generated typed bindings for common providers
- `bindings_generator` - generate typed Rust bindings from a provider schema (`bindings_generator` feature)
- actions for the deploy lifecycle: validate, plan, deploy, watch, show, destroy (`deploy` feature)

## Bindings

The committed provider bindings (`bindings`) are generated, never hand-edited: regenerate with `just bindings`. A provider bump is a two-line deliberate act, edit its `schema_version` in `terra::Provider` and rerun, which is what makes generation reproducible (`Provider::version` floats and would not).

Every generated resource implements `terra::ToJson`, whose output is a `beet_core::Value` rather than a `serde_json::Value`, so a rendered body enters `terra::Config` in the type the config already holds and no conversion sits at that boundary.

## Deploy and teardown

A stack's `deploy` and `destroy` are two `Group`s, named by `<DeployRoutes deploy={$up} destroy={$down}/>` and run forward and in reverse. Both are authored in CONVERGENCE order, teardown included: what a deploy needs first is what a destroy removes last, so there is only ever one ordering to keep right and no second list to drift.

`tofu` is an element of that order rather than the whole of it. A terraform-owned resource gets its lifecycle for free, but anything created outside it (a wrangler Worker, an elastic ip's reverse record, a create-if-missing parameter) has a create path and nothing else unless something declares its removal. So a teardown group reads:

```bsx
<Group bx:ref="down">
    <StackTeardown/>              // the state carriers, converged before the apply
    <TofuDestroy/>
    <Group bx:ref="attach_down"/> // whatever attached after it
</Group>
```

`<StackTeardown/>` owns the four state carriers: the three the driver used to sweep in a hardcoded call no block could add to (the tofu state object, the native S3 lock beside it and the work directory) and the stack's parameter store prefix, which holds every secret an action minted outside terraform (`<EnsureSecret/>`, a DKIM key, a mailbox credential) and which the driver never swept. They converge before the apply, so reversed they come off after it, the secrets last of all since they are minted first; the sweep names each parameter it deletes and never a value. The repo store is not a carrier: it is a declared block, so `tofu destroy` removes it with everything else.

The `attach` groups are where a declaration joins. A paired declaration (`<EipReverseRecord up={$attach_up} down={$attach_down}/>`, `<MtaStsPolicyHost .../>`) spawns its up-action and its down-action from one tag at one file position, so both groups' member lists are projections of the same insert order and cannot drift apart. Every down-action must succeed against an absent resource: a destroy walks the declarations, not a ledger of what was created, because a ledger records what WAS created rather than what SHOULD exist and a half-failed deploy leaves exactly the unrecorded resources you most want cleaned up.

`--force` on `destroy` selects the continue-on-failure run mode, so every member runs and the failures are reported at the end.

A destroy is denied for anything the config no longer DECLARES. The deployer's policy is lowered from the declarations (`DeployerPolicy`), so removing a block and then tearing the stack down leaves a resource in state that nothing is permitted to delete, and the symptom is an `AccessDenied` on a service the policy no longer names. Put the declaration back, destroy, then remove it.

The converse, a declaration leaving the apply while its resource lives on (adopted by a verb, handed to another stack), is `forget --resources=<address>,..`: each address, spelled as `list` prints it, leaves the stack's state and the live resource is untouched, so the next plan does not destroy what the config stopped rendering. `tofu import` is the way back.

A stack's state is client-side encrypted by default (`StateEncryption`, OpenTofu's pbkdf2 + aes-gcm): `Stack.state_passphrase` names the environment variable the passphrase is read from, `TF_STATE_PASSPHRASE` unless declared, one record of the entry's secrets document shared by every stack the repo declares (`secrets/set TF_STATE_PASSPHRASE --generate`), so a new stack is encrypted by forgetting rather than plaintext by forgetting and a missing variable fails `tofu init` rather than downgrading. A throwaway opts out with `state_passphrase={None}`. Every tofu variable rides the child's environment as `TF_VAR_<key>`, never argv. Rotating the passphrase is `rotate-state`, once per stack: `secrets/set TF_STATE_PASSPHRASE_OLD --copy=TF_STATE_PASSPHRASE --role=env_var` keeps the retiring value beside the new one, `secrets/set TF_STATE_PASSPHRASE --generate ..` mints it, every stack runs the verb, and `secrets/rm TF_STATE_PASSPHRASE_OLD` closes it. OpenTofu writes pbkdf2's salt into the state envelope keyed by the key provider's ADDRESS (`key_provider.pbkdf2.main`), so a provider under a second name finds no salt and reads nothing, and a passphrase cannot simply be swapped under one name. The verb therefore moves the state out of the primary key's NAME and back, in two writes ([`StateCrossing`]): the first reads under the primary holding the retiring passphrase and writes under a secondary holding the current one, the second reads under the secondary and returns the salt to the primary. **Every write is encrypted under the current passphrase.** That is not tidiness: a backend is versioned, so a plaintext or stale-key write is kept rather than overwritten, and a rotation that made one would publish the state it was run to protect. Each crossing is a `state pull` pushed back with its serial bumped, so a rotation moves the serial by four, and no fallback is ever left in place, since one that stayed would also read a state somebody replaced. The same verb encrypts a stack whose state is still plaintext (`FromPlaintext`, the one crossing with an `unencrypted` fallback, which needs no salt), and re-runs as a no-op on one already under the current value. If a rotation is interrupted between the two writes the state is parked under the secondary name; re-running the same command recovers it, which is why `TF_STATE_PASSPHRASE_OLD` is removed only after every stack has planned.

Where that state LIVES is a property of the launch rather than of a stack, so it sits on the `Deployment` resource and every stack in the world shares it: one bucket, a flat key per stack (`<app>--<stage>--tofu-tfstate`), created on first use with object versioning on so a fresh account deploys with no backend provisioned by hand and every overwrite has an undo. Nothing declares it. The bucket is `beet-state-<account-id>`, derived at the launch's first verb from `sts:GetCallerIdentity`, and its region is read off the bucket with `GetBucketLocation`, so the second project an account deploys finds the first one's state bucket and its region with no authoring at all: a global name cannot be a shared default, and a name derived per account is unique by construction. The two forms are separate types, as `Stack` and `ResolvedStack` are and for the same reason: `StackBackend` is the declaration, with a bucket and region it is allowed to leave out, and `ResolvedBackend` is the form that renders and addresses, with neither missing. `StackBackend::resolve` is the one async step between them, memoized per declaration for the process, and a `Project` holds the resolved form, so holding a project is proof the discovery ran and nothing downstream asks whether it did. The world pass that builds a project is sync, so an action resolves first (`Project::resolve_backend`) and hands the result in.

`<S3StateBackend/>` covers the two things discovery cannot know. `region="ap-southeast-2"` is where the bucket is CREATED when there is not one yet, worth declaring in the first project an account deploys and in none of the rest, since an existing bucket is found wherever it is (and a declaration that disagrees with the bucket warns and loses). `bucket="shared-state"` names a bucket instead of deriving it, which every project sharing that bucket then declares. Moving an existing bucket is a copy and a re-init, never a rename: the objects go over server-side, and the next verb re-inits because `init` stamps the digest of the config it FINISHED against (`.beet-tofu-init`) rather than trusting the rendered `main.tf.json`, which is on disk before init runs and would otherwise make a failed init look finished.

## Deploy layers

A deploy publishes into its stores and then rolls the service that reads them, so a deploy route applies once per phase: `<TofuApply layer="storage"/>` creates the resources the fill steps publish into (buckets, tables, the image registry), the fill steps run (image push, content publish), then a bare `<TofuApply/>` converges the whole stack and rolls the service. Blocks declare their publish-into resources with `Config::add_layer_resource`, defaulting the assignment to the `storage` layer and exposing it as a field. Naming a layer no block declares is a loud error, never a silent no-op.

The content publish is two steps: `<RepoStage src="site">` assembles the document in a staging dir under the deploy work directory (its `<DirCopy/>` children borrow workspace-built files into it, so nothing is written into the checkout), and `<RepoSync/>` mirrors that dir into this launch's version of the repo store through `BlobSync`, a store-agnostic mirror that skips objects already matching by size and digest and removes what the stage lacks. A content-only `sync` verb runs `<AdoptCurrentDeploy/>` first, so the same pair publishes into the version being served.

Two footguns the markup cannot yet make unrepresentable:

1. A route with a single bare `<TofuApply/>` is valid markup that reproduces the fill race: the service rolls onto an image tag the push has not created yet and a store the sync has not filled, and the Fargate deployment circuit breaker (always on) rolls the deploy back instead of retrying until the fills land. Always order the layered apply and the fill steps before the bare apply.
2. A block that forgets `add_layer_resource` on a resource a fill step writes into wedges the first deploy rather than racing it: the fill fails loudly (eg `NoSuchBucket`) and aborts the sequence before the full apply that would have created the resource ever runs, with error text pointing at tofu rather than at the missing layer declaration.

## Declarations

A cloud resource is declared ONCE, in markup, as its provider block (`<S3BucketBlock label="app"/>`, `<DynamoTableBlock bx:ref="events" label="events"/>`). Both meanings hang off that one entity: the deploy meaning (the block's `Block` impl and `DeployRender` systems, always compiled) and the runtime meaning (a live store, attached by an `InfraPlugin` observer). Never derive a resource name a second time.

Retiring a *protected* resource is two applies, and removing the declaration first is the wrong order: with the block gone there is nothing left to turn `deletion_protection` off with, so the destroy fails at the provider. Clear the flag while the block is still declared, apply, then delete the block and apply again.

A block is a declaration, not a sequence step, so nothing dispatches it during a deploy. Anything a block must *do* belongs to whichever step consumes its output, never to the block being run: an artifact is built by the apply that uploads it (`TofuApply` -> `BuildArtifact::build`), because a build wired as its own step is a build some other entry forgets, and an artifact uploaded but never built is a stale binary shipping under a green deploy.

A version is one prefix in the repo store, laid out by `ArtifactLedger`: the document under `<id>/repo/` (the uri a compute bakes and the mirror root a sync writes), each binary under `<id>/bin/`, the ledger beside them, and `current/` holding the served ledger and the per-artifact release pointers. The apply's upload, the sync's destination and `PruneVersions` all compose through that one type, so a document can never outlive its binary or the reverse. A stack shipping a `BuildArtifact` must therefore declare a deploy-versioned repo store, and `TofuApply` names what to declare when it does not; the Lightsail and Lambda blocks read the bucket they boot from off the same declaration (`RepoStoreDecl::bucket_name`), never by a second composition.

Blocks are immutable components (reinsertion is the only mutation path). `ErasedBlock` is the data projection of any block (its label and artifact label), derived by a generic `on_insert` hook so it can never go stale, removed with its block, and one per entity: a second block type on the same entity raises a clobber error rather than silently retagging it, mirroring `beet_action`'s one-action-per-entity rule.

A block whose resource is a store (a bucket, a table) adds `StoreBlock` (`store_uri`/`deploy_versioned`), and `ErasedStoreBlock` is its projection: the root `StoreUri` resolved against the stack, which every consumer of "the store, whichever kind" reads (the sync's prefix, the ledger's record, the uri a compute bakes), beside the local stand-in uri for the same declaration. The one runtime attach observer asks `runtime_uri` which of the two this launch's `ServiceAccess` means and builds it through `StoreProvider::from_uri` on every target (a store kind this build has no backend for errors with guidance at attach), so a store block defined anywhere attaches without being named. `<StoreUriBlock label=".." uri=".."/>` is the store block naming a store this deploy does not create. The store an app is served from is whichever store block carries `{RepoStoreBlock}`: one per world, found by type through `RepoStoreQuery` and never by label. A template that needs it at build (a compute baking the uri it boots from) resolves it in an `On<Ready>` observer through `RepoStoreQuery`, since a sibling declaration may be a forward one whose erased half has not landed at spawn.

## The render

The deploy render is the `DeployRender` schedule. `RenderScope` is a component the seam (`RenderScope::render(world, entity)`, or `render_all` for every declared stack in one run) inserts on the stack root and takes back out, which is the whole reset. Every block system reaches UP to the nearest scope (`AncestorQuery<&mut RenderScope>`) and writes to it directly: `Declare` states grants and tofu variables, `Render` emits resources; computes lower the pool, so `Declare` runs first. `AccessGrants` is a sorted set by construction, so contribution order can never matter and a reordering of declarations never diffs a rendered policy. Render errors collect on the scope and fail the call before any tofu invocation, so one render reports every misconfiguration.

A block's data shape is the `Block` trait (`label`/`grants`/`variables`/`artifact_label`, never `dyn`, no world access). A simple block adds `EmitBlock::emit` and rides the generic `declare::<T>`/`render::<T>` systems; a block with cross-entity inputs (a relation, an artifact, the pool) writes its own render system in the same reach-up shape.

## Identity

A resource belongs to the stack it is authored under, and to no other: `StackQuery::declared` is the stack root's inclusive descendants, full stop, with no adoption sweep. A declaration outside every `<Stack>` still resolves the process default for its runtime meaning, but no deploy provisions it. Load-bearing identity rides `<Stack>`, a component registered in every native build, never a template prop: a prop is absent exactly in the binary that did not link the template, which is a lean boot silently resolving the wrong stage.

A declaration carries only its **label**, and identity is two types: the authored `Stack` (the app and stage, each optional and falling back to the nearest ancestor `<Stack>` else the process, plus the tofu-level state settings) and the total `ResolvedStack` it resolves to, the only type that composes `<app>--<stage>--<label>`. App identity lives in exactly one place, `PackageConfig::app_name`. Reach both through `StackQuery`; one-launch mechanics (the state backend, the work dir, the deploy id every artifact is keyed by) live on the `Deployment` resource. See the `Stack` docs for the whole model.

`Stack` is provider-agnostic. Where its resources land at a provider is a **provider address**, a component spread on the stack or any ancestor and resolved by ancestry from the entity that asks: `AwsRegion("ap-southeast-2")`, `CloudflareAccount("..")`, `CloudflareZone{domain:"beetmash.com", id:".."}` (`types/provider_address.rs`). A shared address sits on the root (`<Router {AwsRegion("..")}>` serves every stack under it), a block that genuinely needs another zone carries the same spread itself, and no block has an address field of its own (the tofu aws provider is configured once per stack, so a per-block region field could not do what it said). `StackQuery::resolve(entity)` reads the nearest of each into the `ResolvedStack`, whose `aws_region()`, `cloudflare_account()` and `cloudflare_zone_holding(record_name)` answer `Result`, failing by name ("declare `{AwsRegion(\"..\")}` on the stack or an ancestor") rather than falling back: the environment is never consulted, since a region that could silently fall back plans a full replacement, and a Cloudflare record whose name the declared zone does not hold is refused at render, the cheap guard against a wrong spread. `RenderScope` fails fast on a stack with no region, and the generic render systems resolve the stack per block entity, so a block-level spread renders with it. The ids are identifiers, public in every dashboard url, and belong in committed markup, never in a secrets document.

A store (`S3Store`, `DynamoStore`) sits below `Stack` in the crate graph, so it cannot resolve an ancestor stack. Stack-relative resolution belongs to the declaration, whose erased half carries the declared region in its root uri (`StoreBlock::store_uri` is a `Result`, so a bucket under a stack with no `AwsRegion` never lands a store the deploy would not have created); the only public store constructor makes a caller name a region. Locally the same declaration attaches an `FsStore` under `target/stores/<app>--<stage>--<label>` (in a browser, one IndexedDB database of that name): the erased half carries that stand-in uri beside the root, `ErasedStoreBlock::runtime_uri` picks one by `ServiceAccess`, and `StoreProvider::from_uri` builds it. No attach site matches on a store kind.

## References

A runtime consumer names the declaration through a relation, never a name: `<Router {(AnalyticsConfig, StoreRef($analytics))}>`. A consumer with nothing to point at is a loud error naming what it is missing, not a silent local fallback. `StoreRef` is the one-store case and what `StoreRef::resolve` reads off, backing off first because a declaration's runtime half lands through the command queue. A consumer of SEVERAL stores names them in ONE place, one field per role, never a generic relation plus a specifically named one per extra store: the generic name would be silently role-bearing, and half a pointing would be authorable. Where the consumer is an action and nothing else needs the same set, the fields are the action's own (`<Route path="rollup" {AnalyticsRollupJob{raw: $analytics, rollups: $analytics, archive: $archive}}/>`, each `#[field(required)] #[entities]`), so the requirement is in the signature and a missing store is an error naming the field. Where several consumers share one set, it is one component they all carry (beet_egress' `LogRef{store, index}`, read by four verbs). Either way two fields may name one declaration, which is how a deployment collapses two keyspaces into one bucket.

A `<DirSync>` names its LOCAL end the same way where that directory is a declared store: `<DirSync bucket="store" {StoreRef($store)}/>` syncs the store the declaration roots, spelling the path once, and `local_dir="site/assets"` stays the form for a directory no declaration owns. The local end is resolved when the sync RUNS, beside the deploy prefix and the storage class and for the same reason the observer cannot: a declaration's runtime half lands through the same command queue, so only an async caller can wait for it.

A deploy-time reference from one block to another rides the same relation model (`VpcRef`, `DatabaseRef`, `InvokeTarget`, each targeting the declaration entity via `bx:ref`): the target block owns the ident composition, the consumer's render system reads the target's block through the relation and asks it to compose, and a missing, dangling or out-of-stack target is a collected render error naming the relation, before `tofu plan` ever runs. `SecretRef` stays a label (`dkim-example-com`): a secret is created by `EnsureSecret` at deploy time, so there is no declaration entity to target, and the stack's secret store composes its own address from the label (see Secrets below).

## Secrets

The human side (one age identity per person, the `secrets.toml` beside an entry that the launch loads before the entry builds, the `vault` and `secrets` verbs) is `beet_core::secrets`, `beet_net::secrets` and the [secrets tutorial](https://beet.org/docs/secrets); this crate owns the stack side, under the `vault` feature `deploy` turns on.

A stack's tier 2 secrets (everything an apply or a provision mints: the SES relay pair, a bucket token, a mailbox password, the sovereign DKIM key) live behind one seam, `SecretStore` (`types/secret_store/`), the erased-provider pattern (`AGENTS.md`) scoped to one stack exactly as a `BlobStore` is scoped to a bucket and prefix: `get`, `require`, `create` (never an overwrite, so two racing deploys cannot each believe theirs is in use), `overwrite` (for a value another system mints and the store mirrors), `ensure` (create-if-missing with the race re-read, the one shape every generated credential takes, converging an existing entry's note and rotation to the declaration around its unchanged value), `list` with metadata, `read_all`, `delete`, `address`, and `for_stack` (the `with_subdir` of the seam, how a drill reads its source stage's credential). Every method takes a `SecretRef` label alone and the provider composes its own address, so a label never couples to a provider and an export restores into another provider or region unchanged. Two providers ship: `SsmSecretStore` (AWS parameter store in the stack's region, over the `aws` cli, native and `deploy`) and `DocumentSecretStore` (a secrets document, on every target, refusing any stack but its own). A stack's store resolves from a declaration on or under its `<Stack>`, `<SsmSecrets/>` or `<DocumentSecrets path="infra/secrets/app--prod.toml"/>`, and a stack with none carries an implicit `<SsmSecrets/>`. The declaration is absolute, whatever the launch's `ServiceAccess`: every stack verb reaches the cloud (an apply, a provision) and addresses the declaration's meaning, exactly as a sync addresses a bucket's `store_uri` and never its runtime stand-in, so a deploy can never mint a stage's secrets somewhere its box does not read (`SsmSecrets::store`). A stand-in for a run with no account is an explicit `<DocumentSecrets path="target/secrets/app--dev.toml"/>`, the way an `FsStore` is explicit in a test; `validate` reads no store at all. Two declarations under one stack is an error naming both. Grant lowering stays with the compute (`ssm:GetParameter` on an AWS box): it is the cloud runtime's access path and legitimately provider-specific, and so are the terraform-emitted parameters a block declares (`SecretRef::parameter_resource`), which is why `SecretRef::name` keeps the `/app/stage/label` composition.

Every mint declares how its secret rotates, as a `SecretRotation` stored beside the value (a document record's `rotation`, a parameter's description): `replace:<resource>` for a terraform-derived secret (`tofu apply -replace`), `remint` for a create-if-missing one (delete the entry and the next deploy mints afresh and re-provisions its consumer, which is what `<EnsureSecret/>`, a mailbox credential and the DANE pin declare), `manual:<why>` for what only a hand rotates (a DKIM key, whose rotation is a new selector). A mint site cannot omit it: `SecretStore::create` and `SecretRef::parameter_resource` take one. Every mint also names its secret in one line with the address in it, the `note` stored beside the rotation (`password for account pete@example.com`, `administrator credential for mail.example.com`, `DKIM signing key for example.com (selector stalwart)`, `SES relay smtp user for app`, `R2 token for bucket cold-backups: access key id`, `DANE pin for mail.example.com`, and whatever `<EnsureSecret note="..">` declares), so an export and `secrets/ls` say what each record is without the declarations in hand; `ensure` converges an existing entry's note and rotation to the declaration. A secret parked by hand (a comail enrolment) has none and is listed as such.

A tofu `Variable` reads the store as one `VariableSource` among the ambient ones (`ProcessEnv`, `Header`, `Param`, which a pipeline supplies at apply and which carry an empty terraform default): `Variable::secret(key, SecretRef)` is CONTENT, resolved by every rendering verb through the store and refusing when absent, and `Variable::secret_optional` is the same source with absence a legal state (a `TLSA` before any certificate exists), rendering empty. The store is the one source where absence is a runtime state that changes over time, which is why `optional` lives on that variant and not on every variable; `sensitive` stays a property of the use, never implied by the source, since the two store-backed variables today (the DKIM public key, the DANE digest) are public halves.

Three verbs work the seam. `<SecretsExport document={$d}/>` writes the whole store into the secrets document `$d` declares (a committed `infra/secrets/<app>--<stage>.toml`, rewritten only when a secret changed; with `dated=true` a `YYYY/MM/DD/HHMMSSZ.toml` series beside the declared path, ie in the cold bucket), one record per label with its note, address, modified time and rotation, sealed to the recipients of the entry document's group; it ends every deploy and provision, and a stack mounts the same two steps under `secrets/export` for the day the copies should follow now. A declaration targeting an `R2BucketBlock` is written under the pair the apply parked (`R2BucketBlock::parked_store`), resolved by the verb rather than at attach, which is also why `secrets/check` reports such a document as a note rather than reading it: `cold-probe` is the verb that reads it back. `<Route path="secrets/restore" {SecretsRestore}/>` is the inverse, writing a document (`--document`, `--from` a dated key, `--only` labels) back through `overwrite`, refusing without `--force` where the store already holds a label. `<Route path="secrets/revoke" {SecretsRevoke}/>` removes a human: refuses while `--recipient` is still in any group's list, re-seals every declared document, then rotates every secret of the store by its declared rotation and prints the manual residue; `--dry-run` prints the ledger alone. Both answer a report, so each rides its route as a leaf, where the export's steps sit under `{ExchangeSequence}`.

A downstream provider is one trait impl plus a reflect declaration plus an attach observer, the shape `attach_document_secrets` gives the document store. The 1Password cli as the worked example, not implemented here: `OpSecretStore { vault, stack }` implements `SecretStoreProvider` with `address` composing `op://<vault>/<app>--<stage>/<label>`, `for_stack` the same vault under another stack, `get` running `op read <address>`, `create` and `overwrite` running `op item create|edit` (the note and rotation in a text field), `list` running `op item list --vault <vault>` filtered by the `<app>--<stage>` prefix, and `delete` running `op item delete`; `<OpSecrets vault="infra"/>` is a `#[derive(Component, Reflect)]` the crate registers, and its `On<Insert, OpSecrets>` observer queues a command that resolves the stack through `StackQuery` and inserts `SecretStore::new(OpSecretStore { .. })` on the declaring entity. Nothing in `beet_infra` names it; `StackQuery::secret_store` finds it by type under the stack like any other.

## The deployer

Every verb here runs as an AWS identity nothing declares: the deployer, one IAM user per **credential document** (so per repo, since a document holds one `AWS_ACCESS_KEY_ID` however many apps a repo deploys), whose pair is an `env_var` record of that document. `<DeployerMint/>`, authored once per entry outside every `<Stack>`, converges it: the user `<repo>-deployer`, one policy per app the entry declares, and one access key, sealed into the document and proven with `sts:GetCallerIdentity` before the key it replaces is deleted. The policies are customer MANAGED rather than inline, because a user's inline budget is 2048 characters for all of its policies together, which three apps of one repo exceed; managed also means an entry converges its own apps' policies and leaves a sibling entry's alone. `--dry-run` prints the policies and touches nothing (and needs no administrator); `--rotate` mints a fresh key over a working one.

The identity lives OUTSIDE tofu on purpose, and it is the one thing about a stack that is not declared. A deployer declared as `aws_iam_user` in its own stack would need `iam:PutUserPolicy` on its own user just to plan, which is an administrator with extra steps; that stack's `destroy` would delete the credential it is authenticating with; and the tier cannot close, since the apply that mints the first deployer runs as some earlier one. Minting is therefore an administrator's act, and the verb is the one that does not run as the deployer it converges: pass an admin pair for the one command (`AWS_ACCESS_KEY_ID=.. AWS_SECRET_ACCESS_KEY=.. beet deployer/mint`), which wins over the document, since the launch's load lets an existing environment variable win.

What the block would have bought is bought anyway: the policy is **derived from the declarations** rather than written by hand. `DeployerPolicy` lowers the provider types a stack renders (`Config::declared_types`) into an IAM document, the deploy-side mirror of `IamPolicy` lowering a stack's grants into what the running process may do, loud on a type it cannot place for the same reason. Per app it grants the identity call every launch makes, the keys named for that app in the shared state bucket (`<app>--*`, which is every stage's state object and the lock beside each, read/write; the bucket itself read-only, since `ensure_exists` and the region discovery ask it on every verb), `s3:*` on the app's own bucket namespace (`<app>--*`), `iam:*` on the app's own roles, users, policies and instance profiles when a stack renders any, `ssm:*` under the app's own parameter prefix (plus AWS's public `/aws/service/` tree, where a compute block reads its AMI id, and `ssm:DescribeParameters`, the one parameter call that takes no resource), and `<service>:*` for everything else, conditioned on the regions the stacks declare.

Every NAME is per app rather than per app and stage, so one mint covers every stage: the pair is per repo, so the same key already deploys `dev` and `prod`, and a stage split would draw a boundary the key does not have. The SERVICES are still one stage's, because a launch renders one stage and a stage may declare more (a prod site has a certificate and a custom domain its dev stage has neither of), so a mint runs under the stage that deploys, `--stage=prod` where that is not the default, and warns when a stack took a non-prod launch stage. A provider a policy does not grant surfaces as an `AccessDenied` on the next plan, and a re-mint fixes it; a provider TYPE the lowering cannot place fails the mint by name instead, which is the only way a new service reaches the policy on purpose.

That last statement is where it stops being least privilege, deliberately: an action-level list per service is unverifiable without applying every path of every stack, and a provider refresh reads far more than a deploy writes. What the scoping buys is that a leaked key is one app's blast radius in one region, with no IAM outside that app's names, no reach into another app's buckets or state, and nothing at the account level. Two things it cannot know need a statement by hand: a bucket outside the app's namespace (a `<StoreUriBlock>` naming another app's store), and a resource the config no longer declares but the state still holds.

## The permissions boundary

`iam:*` on an app's own names bounds what a deployer can REACH, not what it can GRANT. Three calls turn it into an administrator: create `role/<app>--prod--anything`, attach the AWS-managed `AdministratorAccess` to it (the resource `iam:AttachRolePolicy` checks is the role, which is in scope), pass it to a compute the same policy may create. A **permissions boundary** closes that, because the effective permissions of a boundaried principal are the INTERSECTION of its own policies and the boundary, and the boundary grants no `iam:` action at all.

`RuntimeBoundary` derives one managed policy per app and STAGE, `<app>--<stage>--runtime-boundary`, from what that stage's stacks RENDER: the union of every `aws_iam_role_policy` and `aws_iam_user_policy` body (each of which is `IamPolicy`'s lowering) plus the AWS-managed policies those principals attach. So the cap is exactly "no principal this stage creates may ever exceed this stage's runtime needs", said in the same words the runtime identities use. `deployer/mint` converges it beside the deploy policy from the same render, and every block that renders a principal sets `permissions_boundary` on it.

**Per stage and not per app**, unlike the deploy policy beside it, because a launch renders one stage and the names a boundary grants are that stage's. A prod-derived boundary worn by a dev role intersects with that role's own policy to nothing, and the dev process then fails to read its own bucket with no error anywhere. The deploy policy can be per app because every name IT scopes is stage-independent; a boundary's content is not.

Three things the derivation is loud about, all for the same reason — an intersection fails SILENTLY, so a boundary one statement short of what a principal needs stops that principal working with no error anywhere:

- a managed policy the app attaches that `RuntimeBoundary::MANAGED` does not name fails the mint. AWS's own service-role policies are mirrored verbatim, `Resource: "*"` included; narrowing them is a change to prove against a live runtime rather than to guess.
- a rendered document pointing at a resource rather than naming it (`${aws_lambda_function.x.arn}`, the scheduler's invoke target) is resolved through `RuntimeBoundary::ARN_SHAPES`, and a type with no shape declared fails the mint. A policy created outside tofu cannot carry a tofu reference.
- a grant added to a stack widens the rendered runtime policy but not the boundary until the next mint, which is the same cadence a new SERVICE already has.

### The order of operations, which the mint enforces

A `StringNotLike` deny on `iam:PermissionsBoundary` (a pattern, since one policy spans every stage and each stage has a boundary of its own) is TRUE for a principal carrying no boundary, which is what makes it refuse to edit an uncapped one — and also what would deny the very apply that attaches the first boundaries. So the order is: converge the boundary, apply each stack so every live principal gains it, only then condition the deploy policy. `deployer/mint` decides by asking the account whether each principal the render names already wears the boundary, so the order is enforced rather than remembered: the first mint of an app with live uncapped principals writes an unconditioned policy and warns, and the next one closes the door. An app whose principals do not exist yet is conditioned from birth, since its `CreateRole` carries the boundary.

Deny rather than Allow throughout, because the `Iam` statement is a broad `iam:*` Allow and only a Deny restricts it. `iam:PassRole` takes no boundary condition at all and is bounded instead by that statement's own `role/<app>--*` resource: with every role in the namespace capped, there is no uncapped role to pass.

One consequence to know before conditioning a policy: the deny covers `iam:DeleteUserPolicy` and `iam:DetachUserPolicy`, and destroying a principal means deleting its inline policy first. So **an uncapped principal cannot be destroyed by a conditioned deployer either** — the same `StringNotLike` that refuses to edit it refuses to dismantle it. Renaming a principal that predates the boundary therefore has to happen while the policy is still unconditioned, which is the order the mint already enforces, and it is also why reverting such a rename after the door has closed needs an administrator.

### The speed bump on the irreversible

Everything else a deployer may do is recoverable by design: a bucket is versioned, a table has deletion protection, a noncurrent version has a window. The small set that is not — `s3:DeleteBucket`, `dynamodb:DeleteTable`, `rds:DeleteDBInstance` on `<app>--prod--*` — is denied unless MFA is present. A deployer never performs any of them, so it costs nothing day to day and makes destroying production a human act.

Three actions that belong to that idea are **deliberately absent**, because a deny is absolute and an action a converge needs would block every apply: `s3:PutBucketVersioning` (every new bucket is created with versioning enabled, and IAM has no condition key for the versioning STATUS, so a deny cannot tell enabling from disabling), `s3:PutBucketLifecycleConfiguration` (set on every converge), and `iam:DeleteRole`/`iam:DeleteUser` (renaming a principal is destroy-then-create, and a principal is re-mintable from the declarations anyway). **Turning versioning off therefore remains within a deployer's reach**; what stands in for it is the render-time refusal below, which stops a bucket being declared without a way back in the first place.

`BoolIfExists`, never `Bool`: `aws:MultiFactorAuthPresent` is ABSENT from a long-lived access key's requests rather than false, so a `Bool` deny would not fire for exactly the credential it is aimed at. Scoped to `<app>--prod--*`, so tearing a dev stack down stays free.

## Grants

Permissions are declared by the resource (`Block::grants` -> `AccessGrant`) and **lowered** by the compute block, which for the AWS computes is the shared `IamPolicy`: it seeds the statements the compute needs on its own account (the repo bucket it boots from, a log group) and lowers the stack's grants into read/write bucket and per-table statements. A compute whose lowering yields nothing emits no policy resource at all, never a managed `FullAccess` one; per-compute needs ride knobs on the shared core, never forks. A resource block never writes an ARN; a compute block never names a sibling resource.

An `AccessGrant` is `{kind, name, permissions}`: `kind` is a plain string constant the declaring block owns (`S3BucketBlock::ACCESS_KIND`), so a new provider mints `"r2_bucket"` without touching shared code, and the ARN region comes from the compute's own resolved stack. Lowering is **loud on unknown**: a kind the compute cannot lower fails the deploy naming both the kind and the compute, and there are no `_ =>` catch-alls in grant handling (a silently dropped grant is a box that serves until the first request touching that resource).

## Bucket profiles

A bucket is one of three profiles, and the label names the profile:

- `repo` is deploy-mirrored content: the sync owns each version's `repo/` tree (and prunes what it did not put there), the apply publishes the binaries and ledger beside it, and the runtime holds a read-only grant on the bucket. The `assets` buckets (public, stage-shared) are a public variant of this profile with no versioning.
- `archive` is its inverse (`<S3BucketBlock label="archive" runtime_write=true object_versioning=true deploy_versioned=false/>`): append-only cold data no deploy sync ever touches. It holds backup dumps AND primary archives such as compacted analytics days, which is why it is not called `backups`: a bucket named for backups invites treating a sole copy as expendable. Cold data declares its class once on the bucket (`storage_class="GlacierIr"`, see `S3StorageClass`): the deploy renders a day-zero lifecycle transition that moves every object already in the bucket in place, no re-upload, and a `<DirSync>` push reads the same declaration to land new objects there directly, so a sync can never disagree with its bucket. Content that is immutable per path also wants `{SyncS3Bucket{size_only:true}}`: the cli otherwise compares modified times, and a hydrated checkout's files are all newer than the objects they came from, so the next push uploads the whole store back.
- Workload-named buckets such as `analytics` hold runtime-written primary data. They set `runtime_write=true` and `deploy_versioned=false`; analytics segments delete only after the archive and JSON-over-blob rollups verify. A bucket is the unit of IAM grant, so it earns its place by a different writer or a different durability grade rather than by holding a different dataset: raw segments and aggregate rows share one bucket under disjoint prefixes, while the sole-copy archive is its own.

`<R2BucketBlock label="cold-backups" location="weur" retain_days=30/>` is the fourth profile, and the one that is not in the account: a Cloudflare R2 bucket created by the same apply, for the copy that survives losing the AWS account. It composes its name and its `expire_prefixes` exactly as an S3 bucket does, and differs in what it cannot do. R2 has no object versioning, so a prefix not named in an expiry is kept forever and a delete is final; what stands in for the undo is `retain_days`, a bucket LOCK that refuses a delete and an overwrite of anything younger than its window, the parked token and a lifecycle rule included (so a lock may not outlive an expiry, and a bucket declaring no window at all is refused unless it says `accept_data_loss=true`). No IAM policy can grant R2 either, so the bucket answers to an account-owned api token scoped to its objects alone (its id is the S3 access key id, the sha256 of its value the secret), parked in the stack's secret store (`<label>-access-key-id`, `<label>-secret-access-key`) exactly as the mail box parks its SES relay pair; the block's grants name those two secrets and an AWS compute lowers them to `ssm:GetParameter`. **The apply mints nothing**: creating a token needs `Account API Tokens Write`, which can mint any token the account can hold, and Cloudflare has neither a permissions boundary to cap that with nor an mfa condition to put on it, so an apply that minted here would put the escalating group into the deploy credential of every repo declaring a bucket. `beet cloudflare/mint` mints it instead, with a credential that lives in the password manager and in no document, and `R2BucketBlock::missing_credential` names that verb when the pair is not parked. A `StalwartBlock` naming it as `cold_bucket` installs a nightly timer beside the snapshot's that copies the newest snapshot and every blob across (copy, never sync, every copy `--ignore-existing`, so this side only appends), and the mail deploy verbs (`MailColdPush`, `MailColdProbe`, the drill's `source_snapshot="Cold"`) read it back from the deploy machine with the same parked pair, as does a `<SecretsExport/>` whose `<Secrets>` targets the bucket through `{StoreRef($cold_backups)}` (`R2BucketBlock::parked_store`).

Sharing a bucket means sharing a **write grant**. A grant is whole-bucket (`Block::grants` names the bucket, never a prefix), so prefix ownership inside one is writer convention and nothing more: co-locate two datasets only when their writers already trust each other, and give data with its own trust boundary its own bucket and its own grants. What a prefix CAN say is retention: `expire_prefixes={[{prefix:"sqlite/", expire_days:180}]}` renders one filtered lifecycle rule beside the unfiltered `expire_days`/`expire_noncurrent_days` ones, so an `archive` expires a nightly SQLite snapshot while the sole copy beside it is kept forever. The trailing slash is load-bearing (`sqlite` also matches `sqlite-old/`), a rule id derives from its prefix rather than declaration order, and a zero-day or id-colliding rule fails at render rather than at apply.

### What a compromised deployer is defeated by

A deployer key is used every day, so the protection for it is recoverability rather than prevention: prevention costs ergonomics, recoverability does not. Each durability flag defeats a different half of that, and only one of them is enforced:

- **`object_versioning=true`** defeats an overwrite and a delete: both leave the previous version behind, so a bad write is an undo rather than a loss. **A bucket that can be overwritten in place and declares neither this nor `accept_data_loss=true` is refused at render** — either writer counts, the runtime (`runtime_write=true`) or a deploy sync that does not nest per run (`deploy_versioned=false`). The override is named for what it admits, not for what it enables. It does NOT sweep the delete markers a versioned delete leaves: `expire_noncurrent_days` expires the versions and the markers stay, so `ListObjectVersions` on a long-lived bucket grows even after its data has gone.
- **`force_destroy=false`** defeats `destroy` on a non-empty bucket, so a teardown of the wrong stage stops at the bucket rather than emptying it. Every source of record sets it.
- **`expire_noncurrent_days`** decides how long the undo lasts: 90 days by default, `0` forever. It is the one flag that trades recoverability for a bill, so a bucket wanting a longer window says so.
- **`deploy_versioned=true`** defeats a bad publish without versioning at all, by nesting each run's objects under its own deploy id: nothing is ever overwritten and `rollback` is repointing at the previous id. It is why a `repo` bucket needs no `object_versioning`.
- **`<DynamoTableBlock deletion_protection=true/>`** defeats `DeleteTable` from the apply itself, and `ttl` is the expiry half: DynamoDB deletes only rows carrying the attribute, so the writer decides what is expirable.

None of them defeats a deliberate `s3:DeleteBucket` on production, which is why the deploy policy denies that without MFA (see "The speed bump on the irreversible" above). The two halves are complementary: the flags make an accident recoverable, the deny makes the unrecoverable act require a human.

**`<R2BucketBlock/>` reaches the same end by the other door.** R2 has no object versioning, so there is no undo to declare; `retain_days` declares a window nothing may delete or overwrite inside instead, and **a bucket declaring neither that nor `accept_data_loss=true` is refused at render**, the same shape as the S3 rule above and for the same reason. The guarantee differs and the difference is the point: versioning makes a bad write recoverable afterwards, a lock makes it impossible while the object is young and nothing afterwards. So the three halves of `beetmash-mail--prod--cold-backups` are its lock (nothing in its first month goes, whatever reaches it), its `expire_prefixes` (the snapshots roll at 180 days, `blobs/` and `secrets/` never expire) and the box's copy-never-sync discipline (which a render cannot enforce). A lock lives in bucket configuration rather than in the data plane, so the parked token cannot lift it; the deploy credential can, because the lock is its own declaration, and that shows up in a plan.

### The audit trail

`beet-audit` is a multi-region CloudTrail writing management events to `beet-audit-<account>`, versioned, public access blocked, objects expiring after a year. It is the account's memory of who did what, and it is not declared by any stack: it is account-level rather than app-level, it predates every deployer's namespace, and no deployer should be able to reach it. Created once by hand, which is the one piece of infrastructure in this account that is deliberately not a block.

Management events are also in CloudTrail's own Event history for 90 days with no setup, which is the faster lookup; the trail is what makes an incident legible after that.

Reading it takes an account-level credential, not a deployer's: the bucket is outside every app's namespace precisely so no deployer can reach it.

```sh
# what deleted that bucket, from the 90-day event history
aws cloudtrail lookup-events --lookup-attributes AttributeKey=EventName,AttributeValue=DeleteBucket
# the trail's own objects, one gzipped json array of records per region per five minutes
aws s3 ls s3://beet-audit-<account>/AWSLogs/<account>/CloudTrail/ --recursive
```

Expiry is the **last step of a retention order**, never a policy on its own: `<DynamoTableBlock ttl="ttl"/>` enables only the attribute DynamoDB reads an expiry from, and a row without that attribute is never deleted, so the writer decides what is expirable. The blob-side equivalent is the same order without a TTL to stamp, and it is the reference implementation (`AnalyticsRollupRun` in `beet_net`): merge a complete day's segments into its durable archive, write its json-over-blobs aggregate rows, confirm both by reading them back, and only then delete the source segments. An S3 lifecycle rule may optimize the cleanup either way, but app correctness never depends on one.

## Networks

`VpcBlock` declares its topology rather than assuming one: `zones` (region suffixes, default `["a","b"]`) times `private_tier` (default on) is the subnet count, so a single public box declares `zones={["a"]} private_tier=false` for one subnet and a three-zone workload declares three. A zone's `/24` is its position in the list, so appending a zone never renumbers an existing subnet while reordering renumbers all of them. An empty, repeated or over-long zone list fails at config time, where a duplicate ident or overlapping cidr would otherwise surface as an apply-time AWS error naming neither block.

A consumer with a topology requirement states it against the vpc it is related to, at render: `RdsPostgresBlock` refuses a network with no private tier or fewer than two zones, naming the attribute to set. That is the same "loud at render, before `tofu plan`" rule the relations follow, and it is why the requirement lives on the consumer rather than as a floor on the network.

`ipv6=true` makes the public side dual-stack: an Amazon-provided `/56` on the vpc, a `/64` per public subnet at the same index its `/24` takes (`cidrsubnet` at apply, since the `/56` is only known then), and a `::/0` route to the same gateway. The private tier stays v4-only on purpose, because every v6 address is globally routable and a private subnet with one has exactly the path off the vpc the tier promises not to have. A consumer opts its own side in: `StalwartBlock` takes one address out of the subnet's `/64` (`ipv6_address_count`, an in-place change on a running instance) and publishes an `AAAA` beside its `A`, read off the instance. Let's Encrypt validates over v6 first when an `AAAA` exists and falls back to v4 only on a network error, so a dual-stack box whose v6 path is broken at the TLS layer stops renewing; the restore drill, deployed dual-stack, is the standing rehearsal of a fresh issuance with an `AAAA` present.

## Topics

`<SnsTopicBlock label="ses-events" name="beetmash-ses-events" publishers={["ses.amazonaws.com"]}/>` declares the account-wide SNS topic a stack's alarms and event streams fire into, and the access policy that lets each named service publish under an `AWS:SourceAccount` condition (the default policy grants nothing to a service, and a destination SES cannot publish to drops its events silently). The name is stated rather than stack-composed because one topic serves every domain in the account and every existing subscription is attached to it; a consumer in the same scope (`MailDomainBlock`'s `alarms_topic`, `SesRelay`'s `events_topic`) references the resource, which is also the dependency edge a fresh account needs, while a consumer in another stack names the topic and composes its arn against `data.aws_caller_identity`, so a restore drill fires into production's topic without declaring it.

`adopt=true` emits an `import` stanza beside the topic and beside its policy (`terra::Config::add_import`, OpenTofu's `import` block in JSON, whose `id` may be an expression), so the first apply takes over a hand-made topic (`2 to import, 0 to change`) rather than failing on the duplicate name. The stanza is a no-op once both are in state, and the flag comes off after that deploy for one reason: an import of a topic a `destroy` has since taken refuses to apply, so a config still carrying it cannot be redeployed from nothing. Subscriptions stay hand-made: an email endpoint is a person's address, its confirmation is a click in that person's inbox whatever owns the resource, and SNS deletes a topic's subscriptions with the topic anyway.

## Persistent instance data

The Stalwart box is replaceable, but its encrypted gp3 data volume is a standalone resource in the same availability zone. Production volumes default to `prevent_destroy` plus `final_snapshot`; non-production volumes default to disposable so the same declaration can be used for restore drills, and `data_volume_protected` can override either data grade. Its attachment replaces with the instance and stops the old instance before detaching. The volume's availability zone is a reference to the subnet's rather than a second literal, so the two can never disagree. Cloud-init waits for the exact EBS volume-id device, formats only a device `blkid` positively reported as blank (it exits 2 for "no filesystem" and non-zero for every other reason, and conflating those is how a failed read comes to `mkfs` a populated volume), and mounts by filesystem UUID at `/var/lib/stalwart` with `nofail`, so a volume that never appears leaves an ssh-reachable box rather than an emergency shell. `RequiresMountsFor` on the Stalwart and backup units is what stops the service instead.

Every mail deploy places `<StalwartSnapshot/>` immediately before its full `<TofuApply/>`. The action finds the volume by its `Name`, `Project` and `Stage` tags, skips the first deploy before the volume exists, creates a tagged snapshot with the deploy id as its EC2 idempotency token, and waits for completion before the apply may replace the box. It is an interlock rather than a schedule (the scheduled backup is the box's nightly `stalwart-backup.timer`, which produces a verified restore-anywhere copy), so its depth is a rollback depth in deploys. It prunes the lineage it owns down to `snapshot_retain` (3 by default), matching on the `SourceVolumeName` tag it writes: a step that snapshots every deploy and never deletes is an unbounded bill, and a step that deletes anything it did not tag would eat the snapshot somebody took by hand before something frightening.

A destroyed stage's lineage outlives its volume, so a disposable stage declares `<StalwartSnapshotPrune/>` in its teardown group, after `<TofuDestroy/>` in convergence order (the destroy takes the volume, then this takes its history). It is opt-in and never part of `StackTeardown` because a production stack's last snapshots are the last copies of its mail; the action refuses on a protected volume, so the tag copied into the wrong entry fails rather than prunes.

## DANE

`dane=true` on a `StalwartBlock` publishes a `TLSA` at `_25._tcp.<hostname>` pinning the SHA-256 of the public key port 25 serves (`3 1 1`: the leaf rather than the issuer, because Let's Encrypt rotates intermediates unannounced; the key rather than the certificate, because the key survives a renewal). Needs DNSSEC on the zone, since an unsigned pin is ignored. The hazard is the design: a pin that stops matching the served key has DANE-validating senders refusing the session outright, and keeps them refusing until the record or the key changes, so the pin is never typed and never trusted across a deploy. `<MailDane/>` runs AFTER provision (where a fresh data store gets its first certificate), reads the digest port 25 presents on the box with SNI and without (both must agree, see below), parks it at `<label>-tlsa` in the stack's secret store, and a second `<TofuApply/>` in the same deploy publishes it; the record reads the secret as a `Variable::secret_optional`, content that every render resolves and whose absence publishes nothing, so a fresh stack renders no record at its first apply and exactly one at its second. In steady state the pin never moves, because provision sets the ACME provider's `reuseKey` (the pinned Stalwart mints a fresh key per renewal by default), and the second apply is a no-op. `MailHealth` is the standing check: the published pin over DNS-over-HTTPS with `AD`, against the key 443 serves for the hostname.

Two things provision converges for this that a single-domain server never showed. A server holding one certificate per domain and no default answers a peer that sends no SNI with whichever certificate its hash map yields first, which is random per process: found live serving the newsletter domain's certificate on 25 to a non-SNI peer, a name that covers neither the MX nor the pin. Provision therefore sets `SystemSettings.defaultCertificateId` to the certificate covering the box's own hostname, and `MailDane` refuses to pin while the two handshakes disagree.

## Scheduled jobs

A recurring job is a declaration like any other: `<ScheduledJobBlock label="rollup-daily" {InvokeTarget($rollup_fn)} schedule="cron(0 3 * * ? *)" path="rollup"/>` renders an EventBridge schedule plus an invoke role scoped to the one function its `InvokeTarget` names, and declares no grants of its own (what the job may touch is the target lambda's own declared grants). The cron expression is validated at render, so a typo fails the deploy rather than the job. What an invoke delivers is a `ScheduledInvoke` (`beet_net`), the ONE payload type the block serializes and the lambda adapter deserializes, tagged and versioned because a schedule keeps invoking with the payload the last deploy rendered; its status resolves the INVOCATION rather than a response body, since a job whose dispatch failed must fail the invoke or it reports green in every metric.

A job lambda publishes nothing: `<LambdaJobBlock label="rollup" exec_route="jobs" features=".."/>` is the invoke-only counterpart of `<LambdaSiteBlock/>`, rendering the function, role, log group and lowered policy but NOT the function url, gateway, route, stage or anonymous invoke permission (a hostname on such a block fails the deploy). The runtime offers no argv, so `http_bootstrap` bakes into the zip's `bootstrap` and `exec_route` names the verb whose `Router` the invoke's path dispatches into: the job runs a route of the same entry document the site serves from, in its own url space and its own process, so co-residence in one file costs the served site no reachable surface.
